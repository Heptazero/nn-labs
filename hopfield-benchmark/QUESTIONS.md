# 按问题比较联想记忆模型

更新：2026-09-05。目的：先确定想回答的问题，再让兼容模型在同一任务上形成可比较的曲线。

本页是问题目录、现有实现盘点和下一步方案，不是实验结果，也不是新颖性证明。本轮只写文档；共享模型文件、逐问题 Notebook 和新实验尚未创建。

## 从哪里接着做

建议采用“共享模型代码 + 按问题组织 Notebook”。继续使用现有 `a → b → c → d → e → f` 管线：记忆输入、模型存储、损坏线索、检索、测量、展示。

先完善 **Q04：继续检索是在纠错，还是强化错误？** 同时补 Q01 的噪声恢复对照。先接入少量可信实现，验证同图比较链路，再逐个加入其余模型。同步/异步、温度、迭代上限先作为明确记录的模型配置，不把每个选项都扩展成独立课题；当它直接决定结论时再做单独对照。

当前主实现是 [第一阶段 benchmark](./hopfield_benchmark_phase1_colab.ipynb)，约 1962 行代码，六个模型适配器仍内联在同一个 Notebook 中。它有模型注册表和配对运行器，但还没有独立模型模块。仓库版本未保存任何输出，本轮也未执行；不能据此判断用户是否曾在其他 Colab 副本运行过。

| Q11 | 输入根本不属于记忆库时，模型会拒绝还是硬选一条？ | 1982 阈值/陌生状态和实验 8 有相关入口；Benchmark U6 不等于陌生检测任务。 | 已知/未知查询的检测曲线；拒绝阈值在独立验证集确定。Top-1 必选机制本身不能证明模型“认识”输入。 |
| Q12 | 在同样存储或计算成本下，谁更值得用？ | Benchmark U7 有资源图、部分结构预算对照；主比较仍是原生配置，未完成全面同预算比较。 | 横轴实际存储或累计检索成本，纵轴目标成功率；分别报告构建/训练与检索成本。轮数相同不等于 FLOPs 相同。 |
| Q13 | 加入新记忆后，旧记忆怎样遗忘或被干扰？ | 1982 有有限权重/自然遗忘与时间序列章节；没有跨模型在线存储任务。 | 横轴新增记忆数，纵轴旧/新记忆恢复率和更新成本。批量重训、增量写入必须分开。暂列后续。 |

Q01–Q03 是基准底座；Q04–Q07 是本轮讨论的动力学与机制问题；Q08–Q10 在特定模型接入后展开；Q11–Q13 是后续任务与成本边界。它们是当前研究范围的候选清单，不是要求全部同时执行的待办。

## 第一项问题怎样做成 Notebook

Q04 的入口拟为 `retrieval_dynamics.ipynb`，目前尚未创建。

任务固定为：从同一批受损查询恢复指定存储记忆。主要指标是每一轮的 Top-1 目标识别率，辅助指标是输出与目标的距离、终止状态和计算成本。Top-1 只是认对身份，不能代替精确恢复。

先选择 Classical、Polynomial DAM、Continuous Modern 三个已存在实现。Modern 的迭代行为需要先核验；之后加入 FY sparsemax，再接双曲模型。参数差异保留在配置和图注，默认每个模型选一个预先声明的配置。

每轮都记录：`trial_id, model_id, step, predicted_id, top1_correct, reconstruction_error, cumulative_cost, status`。若模型有权重，再记录其熵或最大权重；若有原生能量，单独记录。不得把能量降低或权重集中等同于更准确。

主图使用同一批样本，包含 t=0。辅助汇总同时报告：相邻轮的错→对/对→错，以及相对第一轮的累计变化。纠错率分母用上一轮错误样本，改错率分母用上一轮正确样本，并保留样本数；没有分母时记 N/A。各模型“第一次就错”的子集可能不同，不能把这种条件率直接当作共同人群上的优劣排名。跨模型主比较用全部配对样本，必要时另看预先声明的共同子集。

达到固定点的确定性模型，可在预算曲线上明确按“停止后保持输出”展示；超时或数值失败不能用最后一个成功值悄悄补齐。单步模型仅报告一步，重复调用必须登记为不同检索配置。另画累计计算成本下的成功率，避免把各模型的一轮当成相同开销。

这先是一个探索性比较。发现候选机制后，再冻结预测，用新种子或新数据验证；本页没有预先认定任何模型会赢。

## 分文件方案

模型代码按模型族复用，Notebook 按问题保留实验叙述、配置、组合入口、图与解释。不要把科学选择全部藏进框架。

以下是目标结构，尚未创建；只按实际需要逐项建立：

```text
am_bench/
  models/
    classical.py           # 模型的 b/d 与原生能量
    dense.py               # 多项式/指数 DAM
    modern.py              # 现代与 FY 权重变体
    simplicial.py
    pshn.py
    hyperbolic.py           # 核验后才接入
  tasks.py                 # a/c：数据、查询、任务声明
  runner.py                # 配对、预算、观察器、分批保存
  metrics.py               # e：只用目标与输出测量
  plots.py                 # f：只读结果，不重新检索
hopfield-benchmark/
  QUESTIONS.md              # 问题与进度入口
  PROTOCOL.md               # 比较约定
  retrieval_dynamics.ipynb  # Q04 起步，关联 Q05/Q06
  capacity.ipynb            # Q01/Q02/Q03，共享结果时不重复运行
```

不需要“一条问题立即建一个文件”；强相关、共用一次运行的问题可放同一 Notebook。模型注册表区分模型族和配置，同步/异步不复制一整套实现。

首轮从 benchmark 提取共享组件，先不搬空旧论文 Notebook。提取前后用同一小样本、同一种子比较终态、状态、轨迹；离散结果要求一致，浮点差异使用事先规定的容差。这样先排除文件迁移改变行为，再做新实验。

需要一并修正的边界：

- `retrieve(..., target=...)` 目前让模型访问正确答案以计算误差。拆分后由独立观察器持有 target；模型只接收查询，真值不参与更新或停止。
- 保留结构化 diagnostics；当前 Modern 算出的注意力熵没有被主结果表完整保存。
- 运行来源记录实际加载的代码提交、依赖版本、任务配置；Notebook 在 Colab 改过时也应保存运行副本/代码摘要。运行时查询最新 `main` 不能证明当前内联代码来自该提交。
- 分批保存和恢复进度；当前主实验返回全部结果后才写文件。曲线直接从原始结果重建。
- `unsupported` 是任务不适用，区别于适用模型的数值失败；不能把前者算作零分加入主图。

## Colab 是否够用

判断：适合小规模合成记忆实验与有限模型比较，先用现有 Colab 起步。尚未查看用户当前运行时或实测吞吐，因此不承诺具体耗时，也不建议现在仅为这份计划升级硬件。

当前 benchmark 主扫描是 `N=(64,128)`、`P=(4,8,16,32)`、四档损坏、三个记忆库重复、每库四个目标、六模型，共 **2304 次检索**；每次最多 20 轮。这个数字不包含后面的结构消融、随机初态等附加实验。H6 的大规模 MNIST 入口默认关闭，不应作为首次 Run All 的性能参照。

当前 `a1_make_independent_binary` 默认 CPU，运行器未指定 GPU。异步模型还逐坐标执行 Python 循环并频繁取标量；切换 Colab 的硬件选项不会自动让这段代码受益。批量矩阵读出的现代/FY 模型更适合 GPU；异步模型可批量处理互相独立的查询，但不能为加速擅自改成同步更新。

建议先加一个小规模试跑配置：三个模型、`N=(32,64)`、`P=(4,8)`、损坏 `(0,.1,.3)`、三个记忆库、每库四目标、最多八轮，共 **432 次检索**。这只是待实现的接口/计时配置，不用于研究结论。先跑少量完整配对批次，记录每个模型耗时和内存，再决定正式扫描；小规模耗时不能线性外推到高阶大规模实验。

每批建议控制在约 5–15 分钟内（工程目标，不是已测性能）。把计算放在运行时本地目录，按批次把结果和配置保存到用户指定的 Drive 目录，记录完成的 trial；断线后从缺失项继续。不要逐样本频繁写 Drive，也不要让默认 Run All 同时启动所有问题。

Colab 官方说明：资源/配额/硬件可用性会变化，运行时有寿命，临时文件不会随 Notebook 一起持久保存；GPU 环境不代表代码已经使用 GPU。来源：[Colab FAQ](https://research.google.com/colaboratory/faq.html)，核查于 2026-09-05。
